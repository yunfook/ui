# LLM.md

A field guide for AI coding agents working on **yf-ui**. Read `CLAUDE.md` first for the
short version; read this when you need to actually do something non-trivial in the repo.

---

## 1. What this repo is

`yf-ui` is a **shadcn registry** — a collection of React component source files that
downstream apps install via `npx shadcn@latest add <url>`. The registry, not an npm
package, is the deliverable.

Two parallel use cases share the same `src/` tree:

| Use case | Surface | Audience |
|---|---|---|
| **Registry** — components are copied into consumer apps | `src/components/`, `src/lib/`, `registry.json` → built into `public/r/*.json` | Other teams installing yf-ui |
| **Preview app** — TanStack Router app that demos every component | `src/routes/`, `src/main.tsx`, `src/router.tsx` | Maintainers + visitors at `localhost:3000` |

The preview app is **not** shipped to consumers. Routes exist purely so a maintainer
can open `/ui/<name>` and see the component live next to a copy-pasteable code snippet.

Status: components are being **ported in from a previous project**. Expect new files to
be added regularly; expect inconsistencies that pre-date this repo.

## 4. Architectural rules every component follows

These are derived from the existing components — match the pattern when adding new
ones.

### 4.1 File layout
- Live in `src/components/ui/<name>.tsx` (atomic) or `src/components/combo/<name>.tsx`
  (composed of multiple ui/ components, often with an opinion).
- Export the component(s) directly from the file. No barrel `index.ts`.
- Co-locate tests as `<name>.test.tsx`.

### 4.2 Class composition
- **Always** merge classes via `cn(...)` — never hand-concat strings.
- Define variant strings with `cva()` and **export both** `Component` and
  `componentVariants` (consumers reuse `buttonVariants(...)` via `render` props).
- Prefer Tailwind classes; avoid inline `style` unless dynamic (e.g. transforms,
  CSS custom properties).

### 4.3 Base UI integration pattern
Two flavors show up:

**Direct primitive wrapper** (`dialog.tsx`, `popover.tsx`, `checkbox.tsx`, `select.tsx`,
`switch.tsx`, etc.):
```tsx
import { Dialog as DialogPrimitive } from "@base-ui/react/dialog"
function DialogContent({ className, ...props }: DialogPrimitive.Popup.Props) {
  return <DialogPrimitive.Popup data-slot="dialog-content" className={cn(..., className)} {...props} />
}
```

**`useRender` polymorphic** (`button.tsx`, `badge.tsx`):
```tsx
import { useRender } from "@base-ui/react/use-render"
import { mergeProps } from "@base-ui/react/merge-props"
function Button({ render, ...props }: useRender.ComponentProps<"button"> & VariantProps<typeof buttonVariants>) {
  return useRender({
    defaultTagName: "button",
    props: mergeProps<"button">({ "data-slot": "button", className: cn(buttonVariants(...)) }, props),
    render,
  })
}
```
This is what lets `<DialogClose render={<Button>...</Button>} />` work — Base UI's
`render` prop swaps the underlying element while preserving wired-up props.

### 4.4 `data-slot` everywhere
Every meaningful element gets `data-slot="<component>-<part>"` — used for styling
hooks (`in-data-[slot=button-group]:rounded-md`) and consumer overrides. Don't drop
it when adding parts.

### 4.5 Variant + state attributes
- `data-variant`, `data-size`, `data-state`, `data-open`, `data-selected` are the
  language. Style off these (`data-open:animate-in`, `aria-expanded:bg-muted`)
  rather than React state where possible.

### 4.6 Theme tokens (no hard-coded colors)
Use the CSS custom properties from `src/styles.css`:
`--background --foreground --card --popover --primary --secondary --muted --accent
--destructive --border --input --ring --sidebar*`. Radius tokens go up to
`--radius-4xl` (extended from shadcn's defaults via the `theme` registry item).

Hex/RGB literals only appear for **intentional overrides** of shadcn's variants
(e.g. `bg-red-500` for `<Button variant="danger">`). Don't introduce new ones casually.

## 5. The registry — how shipping works

`registry.json` is the source of truth. Each item declares:

```json
{
  "name": "button",
  "type": "registry:ui",                   // or registry:lib, registry:style
  "dependencies": ["@base-ui/react", ...], // npm deps to install
  "registryDependencies": ["utils"],       // other registry items to pull in
  "files": [{ "path": "src/components/ui/button.tsx", "type": "registry:ui" }]
}
```

`pnpm registry:build` runs `shadcn build` and emits `public/r/<name>.json` for each
item. Consumers run `npx shadcn@latest add https://yf-ui.vercel.app/r/<name>.json`,
which copies the file(s) into their `src/components/ui/`, rewriting `@/*` imports as
needed and pulling in the listed `registryDependencies` recursively.

**When you add a new component, you must also add an entry to `registry.json`.**
Forgetting this means the file exists in-repo but consumers can't install it.

Item types currently present:
- `registry:style` → `theme` (writes CSS vars on init)
- `registry:lib` → `utils`, `color-utils`, `form-context`
- `registry:ui` → every component in `components/ui/`

`combo/` components are also published. Their entries use
`type: "registry:ui"` plus a `target: "components/combo/<name>.tsx"` so consumers
get the file at `components/combo/<name>` rather than `components/ui/<name>`.
List every `ui/` component the combo imports under `registryDependencies` — and
remember its npm deps (e.g. `@tanstack/react-table` for `data-table`,
`motion` for `icon-button`).

## 6. Forms — the TanStack Form integration

This is the trickiest cross-cutting concern. Three layers:

### Layer 1: Context primitives (`src/lib/form-context.ts`)
```ts
export const { fieldContext, formContext, useFieldContext, useFormContext } =
  createFormHookContexts()
```

### Layer 2: Field-aware inputs (`Input`, `Checkbox`)
These read `fieldContext` directly and **auto-bind when used inside a field**:
```tsx
function Input(props) {
  const fieldApi = React.useContext(fieldContext)
  if (fieldApi) {
    // bind value/onChange/onBlur/aria-invalid to the field
  }
  // otherwise behave as a plain <input>
}
```
The same component works standalone (uncontrolled or controlled by props) **and**
inside a `<form.AppField>` block — no separate `<FormInput>` component needed.

### Layer 3: `useAppForm` hook (`src/lib/form.ts`)
```ts
export const { useAppForm, withForm, withFieldGroup } = createFormHook({
  fieldContext, formContext,
  fieldComponents: { Input, Checkbox, FormField },
  formComponents: { SubmitButton },
})
```
Inside `<form.AppField name="x">{(field) => ...}</form.AppField>`, `field.Input`,
`field.Checkbox`, `field.FormField` are all pre-bound. Inside `<form.AppForm>`,
`form.SubmitButton` reads `useFormContext` to disable while invalid/submitting.

### `FormField` (combo)
Wraps label + content + error display. Read `src/components/combo/form-field.tsx` —
the `toggle` prop pattern (one field controls another field's `disabled` state via a
sibling checkbox) is non-obvious and worth understanding before touching.

Validators live in user-supplied **zod** schemas passed to `useAppForm`'s
`validators.onSubmit`. The repo doesn't impose a validation library beyond that.

## 7. Component catalog — what each thing is for

Use this to pick the right component instead of building one from scratch.

| `CapsuleButton` | Two-option pill toggle (e.g. on/off). |

## 8. Common workflows

### Adding a shadcn primitive
```sh
npx shadcn@latest add <name>
```
- Will land in `src/components/ui/`. Open it and check it follows the rules in §4
  (data-slot, cva exports, theme tokens). Edit if needed.
- If it should be re-publishable through this registry, add it to `registry.json`.

### Porting a component from the previous project
1. Drop the file into `src/components/ui/` (or `combo/` if it composes others).
2. Replace any old utility imports with `@/lib/utils` `cn()`, `@/lib/form-context`,
   etc.
3. Swap Radix imports for `@base-ui/react/<primitive>`.
4. Verify variants are defined with `cva` + `VariantProps`.
5. Add to `registry.json` with correct `dependencies` (npm packages it imports) and
   `registryDependencies` (other items it imports from `@/components/ui/*` or
   `@/lib/*`). Common gotchas:
   - any `cn` import → add `"utils"` to `registryDependencies`
   - Base UI usage → add `"@base-ui/react"` to `dependencies`
   - `cva` usage → add `"class-variance-authority"` to `dependencies`
6. Add a preview route at `src/routes/ui/<name>.tsx` (or `routes/combo/...`). Mirror
   the existing layout: `Row` + `RowItem main` (live demo) + `RowItem` (`CodeBlock`).
   Add `<InstallCommand />` near the top.
7. Add an entry to the `components` array in `src/routes/index.tsx`.
8. `pnpm dev` → check `localhost:3000`.
9. `pnpm registry:build` → confirm `public/r/<name>.json` lands.
10. `pnpm test` if you wrote tests.

### Editing styles
- Theme palette / radius scale lives in **two** places: `src/styles.css` (used by the
  preview app at runtime) and `registry.json` under the `theme` item (what consumers
  install). Keep them in sync.
- Don't add Tailwind config files — Tailwind v4 reads `@theme` from CSS.

### Routes
- File-based: `src/routes/foo/bar.tsx` with `createFileRoute('/foo/bar')(...)`.
- The router plugin regenerates `routeTree.gen.ts`; don't hand-edit.
- `src/routes/__root.tsx` provides the back button + devtools wrapper. New top-level
  sections should follow the existing `ui/`, `combo/`, `animation/` split.

### Tests
- Vitest + Testing Library. JSdom env. Run `pnpm test`.
- Tests exist for components with non-trivial interaction logic (e.g. `wheel.test.tsx`,
  `row.test.tsx`). Add tests when porting anything with imperative DOM behavior.

## 9. Pitfalls and gotchas

- **Don't import from `@radix-ui/*`.** This codebase uses Base UI. Old Radix examples
  in stack overflow / shadcn docs need adapting (`<Trigger>`, `<Portal>`, `<Popup>`
  shapes differ).
- **`render` prop, not `asChild`.** Base UI uses `render={<Button>…</Button>}` instead
  of Radix's `asChild`. Don't introduce `Slot`-style helpers.
- **Don't edit `src/routeTree.gen.ts`.** Regenerated on save by the router plugin.
- **Forgetting `registry.json` after adding a component** is the #1 way to ship a
  silent breakage — the file works locally, but consumers can't `shadcn add` it.
- **`registryDependencies` are item names, not file paths.** `"utils"`, `"button"`,
  `"popover"`, etc.
- **`fieldContext` is read with `React.useContext`, not `useFieldContext`** inside
  the bare `Input`/`Checkbox` so they don't error when used outside a form. If you
  add a new field-aware input, follow that pattern.
- **`Wheel` mount timing** — the popup-friendly `useEffect` chain in `wheel.tsx`
  exists because Base UI's popup mounts after a frame. Don't "simplify" it without
  testing inside a popover.
- **`Row`'s height-sync** uses a CSS variable on the parent (`--yf-row-main-height`)
  to avoid layout thrash. Don't replace with JS-driven `style.height` on each item.
- **`packages/yf-row/`** is a standalone npm-publishable build of `<Row>`. It's a
  separate concern from the registry — leave it alone unless asked.
- **Personal handles**: never write the user's personal handles into artifacts. The
  public identity in this repo is `yunfook` (registry homepage:
  `github.com/yunfook/ui`).
